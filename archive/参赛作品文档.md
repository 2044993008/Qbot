## 模块一：用户洞察与问题定义

### 1.1 目标用户

**核心用户画像：Z 世代大学生与年轻职场人（18–28 岁）**

| 维度 | 特征描述 |
|------|---------|
| **年龄层** | 18–28 岁，以高校在校生和初入职场的年轻白领为主 |
| **身份特征** | 数字化原住民，高频使用即时通讯工具，活跃于多个群聊（班级群、社团群、项目群） |
| **行为特征** | 高频使用社交软件，但面临信息过载；注重表达个性，却常因"词穷"而反复编辑消息；依赖定时提醒管理日程 |
| **技术接受度** | 对 AI 工具接受度高，习惯使用 ChatGPT、Copilot 等辅助工具，期待社交产品内置智能化能力 |

**次级用户**：小型团队协作群体（创业团队、学生项目组），需要轻量级 IM + 任务提醒一体化工具。

### 1.2 用户痛点

基于对目标用户群体的深度观察与需求调研，我们识别出以下四大核心痛点：

#### 痛点一：社交表达负担 —— "发消息太麻烦了，想找人代发"
- **场景**：想给 crush/老师/领导/朋友 发消息，写了删、删了写，反复纠结语气是否合适，最终觉得"太麻烦"而放弃。
- **本质**：不是不会写，而是觉得措辞这件小事消耗了过多认知资源。
- **普遍现象**：许多 Z 世代用户在发送消息前会反复修改措辞，纠结语气是否合适，有时甚至会因为"不知道该怎么说"而放弃发送。

#### 痛点二：群聊信息黑洞 —— "找一条消息像大海捞针"
- **场景**：班级群通知被表情包刷屏，事后想找辅导员发布的考试安排，需要翻几百条记录，翻着翻着就烦了。
- **本质**：群聊信息过载，人工检索效率极低，用户期望"有人能帮我找"。
- **普遍现象**：大学生往往同时活跃于多个群聊，消息数量庞大，有效信息被大量闲聊和表情包淹没，翻找历史记录耗时费力。

#### 痛点三：时间管理碎片化 —— "设提醒太麻烦，全靠脑子记"
- **场景**：答应室友明天带书、答应导师周五交报告，打开日历 App 觉得操作太繁琐，干脆赌一把记忆力，结果十有八九会忘。
- **本质**：现有工具（日历/闹钟）操作路径长、门槛高，用户需要"一句话就能搞定"的极简方案。
- **普遍现象**：大多数年轻人并不习惯使用专业日程管理工具，通常依赖临时设闹钟，但闹钟只能提醒时间点，无法关联具体任务内容。

#### 痛点四：社交内容创作门槛 —— "发动态配文案太费脑"
- **场景**：拍了好看的照片想发空间/朋友圈，但配文想了半小时，最终只发了一个 emoji，觉得"算了太麻烦"。
- **本质**：内容创作对用户是额外负担，用户期待"一键生成"的零门槛体验。

#### 痛点五：群聊管理负担 —— "当群主/管理员太累了"
- **场景**：作为班级群/社团群管理员，每天要花大量时间发通知、提醒交作业、处理广告刷屏、欢迎新人，琐碎事务消耗精力。
- **本质**：群聊管理是高频低价值劳动，完全可以自动化，但现有 IM 工具缺乏智能托管能力。
- **普遍现象**：大量群管理员面临繁重的日常管理事务，期待有智能工具分担重复劳动。

#### 痛点六：传统 AI 助手"用完即走"——"想不起来用 AI"
- **场景**：下载了豆包、通义千问，但除了偶尔查资料或写文案，平时根本想不起来打开。AI 能力很好，但离真实生活太远。
- **本质**：传统 AI 助手是"独立工具"，与用户的日常高频场景（社交、沟通）脱节，导致打开频率低、粘性弱。
- **普遍现象**：独立 AI 助手用户往往"用完即走"，而 IM 工具是用户每天高频打开的场景。用户并非不需要 AI，而是 AI 没有融入他们本来就在的社交流程中。

### 1.3 使用场景

#### 场景一：课间 5 分钟 —— AI 润色代发
> **背景**：小李（大二学生）在课间想给社团负责人发消息请假，但措辞一直不满意。  
> **流程**：
> 1. 小李打开 AI 管家，语音输入"帮我给小张发消息说我今晚社团活动去不了，要准备明天的presentation"
> 2. AI 管家自动润色为："小张晚上好～明天要pre，今晚我得在图书馆准备，社团活动这次请个假，下次一定到！"
> 3. 小李口头确认（回复"确认"）后，消息自动发送
> **价值**：将"反复编辑 10 分钟"缩短为"语音输入 + 一键确认 30 秒"。

#### 场景二：期末复习周 —— 群聊历史智能检索
> **背景**：期末考试周，小王需要找到班级群里老师 3 周前发布的重点范围。  
> **流程**：
> 1. 小王对 AI 管家说"帮我找一下高数群里老师说的期末重点"
> 2. AI 管家调用 `search_messages` 工具，返回 5 条匹配结果，包含发送者、内容摘要、时间
> 3. 点击即可跳转对应位置
> **价值**：将"手动翻找 300+ 条记录（约 8 分钟）"缩短为"一句话搜索 5 秒出结果"。

## 模块二：产品方案设计

### 2.1 产品概述

**一句话定义**：QQ管家是一款基于 Next.js 全栈构建的即时通讯网页应用，通过内置 AI 管家（19 项智能工具）实现"聊天 + AI 辅助"的原生融合，让社交表达更轻松、信息检索更高效、任务管理更智能。

**核心定位**：AI 时代的超级流量入口——你的私人 AI 管家。

QQ管家不是"一个带 AI 的聊天工具"，而是**嵌入 QQ 社交生态的智能伙伴**。题目要求的核心是：从"被动响应"到"主动关怀"，让用户感受到被理解、被陪伴。我们将 AI 能力深度嵌入聊天、群聊、动态等核心流程，让管家不只是帮你办事，更能**主动感知场景、理解情绪、提供关怀**——从替你润色消息的"工具"，进化为主动问你"最近是不是累了"的"伙伴"，真正深化情感连接与使用黏性。

### 2.2 核心功能

| 功能模块 | 解决痛点 | 核心能力 |
|---------|---------|---------|
| **即时通讯** | 基础沟通需求 | 私聊/群聊、文本/图片/文件消息、实时推送（Socket.IO）、历史消息分页加载 |
| **QQ 空间** | 内容创作门槛 | 动态发布（文字+图片）、点赞评论、个人历史动态流 |
| **AI 管家** | 表达焦虑、信息黑洞 | 自然语言对话、文本润色（3 种风格）、代发消息口头确认、群聊历史搜索、AI 生图、记忆系统 |
| **定时任务** | 时间管理碎片化 | 自然语言解析为 Cron 表达式、定时提醒/发消息/发动态、任务执行日志 |
| **好友管理** | 社交关系维护 | 好友列表、备注、个人资料卡片、群成员角色标签 |

#### 安全防护矩阵

| 威胁 | 防护措施 | 实现位置 |
|------|---------|---------|
| **身份伪造** | JWT HS256 + HttpOnly Cookie + 7天有效期 | `middleware.ts` / `auth-utils.ts` |
| **CSRF攻击** | 双重令牌（Cookie + Header）+ HMAC-SHA256 + 24h时间防重放 | `csrf.ts` |
| **暴力破解** | 分层限流（Redis滑动窗口 + 内存固定窗口降级） | `rate-limit.ts` / `rate-limit-redis.ts` |
| **输入注入** | Zod Schema 全量校验（登录/注册/消息/动态/Bot/任务） | `validation.ts` |
| **越权访问** | 会话归属校验（私聊owner / 群聊membership） | `messages/route.ts` |
| **XSS** | CSP Header + X-Frame-Options DENY | `next.config.ts` |
| **点击劫持** | X-Frame-Options: DENY | `next.config.ts` |
| **密码泄露** | bcryptjs (cost=12) 哈希存储 | `auth/register/route.ts` |
| **AI滥用** | 用户级请求队列（120s死锁检测）+ 高危操作确认 | `bot/route.ts` |

### 2.4 交互流程

#### 关键路径一：AI 润色代发消息（含口头确认）

```
用户输入语音/文字
    │
    ▼
AI 管家解析意图 → 识别目标对象 + 内容
    │
    ▼
调用 polish_text 润色（可选风格：casual/cute/formal）
    │
    ▼
高危操作检测 → 命中 send_message → 管家以文本形式口头询问确认
    │
    ▼
管家回复："我准备给小明发消息：'不好意思，我今天会晚点到～'，确认发送吗？"
    │
    ▼
用户口头确认（回复"确认"/"好"/"可以"）
    │
    ▼
后端调用 send_message 工具 → 执行 INSERT INTO messages → Socket.IO 推送
    │
    ▼
目标用户实时收到消息，发送方聊天窗口同步更新
```

**口头确认机制说明**：区别于传统的 UI 弹窗确认，管家通过自然语言对话完成确认流程。用户无需点击任何按钮，只需像和朋友对话一样回复"确认"即可。这种设计降低了交互门槛，让 AI 管家的体验更接近真人助理。

#### 关键路径二：AI 管家 SSE 流式对话

```
用户点击"小Q管家"会话
    │
    ▼
进入 /app/chat/[id]（系统自动识别管家身份，启用 Bot 模式）
    │
    ▼
用户发送消息："画一只赛博朋克猫咪"
    │
    ▼
前端显示三球弹跳动画（isTyping = true）
    │
    ▼
建立 SSE 连接：fetch('/api/bot/stream')
    │
    ▼
后端 Agent 引擎执行 generate_image 工具规划
    │
    ▼
SSE 逐字符推送："好的，我来为您生成一只赛博朋克风格的猫咪图片～"
    │
    ▼
前端实时打字机效果渲染（长文本自动加速至 5ms/字符）
    │
    ▼
```

### 2.5 创新与差异化

#### 三维对比矩阵

| 对比维度 | 传统 IM（微信/QQ） | 传统 AI 助手（千问/豆包） | QQ管家 |
|---------|------------------|------------------------|--------|
| **打开频率** | 日均 40+ 次（高频） | 日均 2–3 次（低频） | **日均 40+ 次（IM 原生高频）** |
| **AI 能力** | 无 | 强（问答/写作/生图） | **强（19 项工具 + 执行能力）** |
| **真实世界交互** | 只能聊天 | 只能回答，不能执行 | **能执行（发消息/管群/提醒，未来将桥接点餐/地图/天气）** |
| **社交链** | 有（关系链强） | 无（孤立使用） | **有（AI 能力嵌入社交链）** |
| **用户粘性** | 高（关系锁定） | 低（用完即走） | **极高（关系 + AI 记忆双锁定）** |

**核心洞察**：微信有高频无 AI，千问有 AI 无高频，QQ管家**同时拥有高频场景和 AI 执行能力**，这是传统产品无法复制的结构性优势。

#### 核心差异化

1. **AI 原生融合：管家是"一等公民"，不是插件**：从架构层将 AI 管家设计为独立会话实体（`chat/[id]` 路由自动识别管家身份），拥有 19 项 Tool Calling 能力、结构化记忆系统和完整审计日志。群聊中 `@小Q管家` 即可触发 AI 回复，无需切换应用。未来可扩展为群管理员，自动发公告、欢迎新人、屏蔽广告。

2. **双层 Agent 编排**：独创 ReAct（简单请求）+ Plan-Execute-Observe（复杂请求）自动路由架构。简单问答走 ReAct 快速响应（< 3s），复杂任务（如"先搜索再润色后代发"）走 PEO 精准编排，兼顾速度与可控性。

3. **LLM 驱动的结构化记忆**：区别于简单的"聊天记录存储"，系统通过 LLM 自动提取 5 类事实（preference/fact/event/relationship/goal），向量化后支持语义检索。用户说"我上次参加的比赛"，即使未提"hackathon"关键词，也能通过 Embedding 相似度召回。

4. **口头确认安全机制**：8 类高危操作（代发消息、发动态、生图、删好友、退群等）管家先以文本形式口头告知用户准备执行的操作详情，询问"确认执行吗？"，等待用户回复"确认"/"好"/"可以"等肯定词后才真正调用工具执行。这种自然语言确认方式降低了交互门槛，体验更接近真人助理。

5. **自然语言驱动自动化**：用户通过对话创建定时任务（"每周一上午 8 点提醒我上课"），LLM 自动解析为 Cron 表达式（`0 8 * * 1`），无需学习任何语法。任务类型（提醒/发消息/发动态）由 LLM 自动识别。

6. **通用 LLM 抽象层**：采用 OpenAI 兼容协议统一封装对话、Embedding、图像生成三种能力，切换模型（OpenAI / DeepSeek / 通义千问 / 本地 vLLM）零代码改动，规避单供应商锁定风险。

7. **未来演进：从"减负"到"趣味"再到"主动关怀"**：
   - **减负阶段**（当前）：处理所有你觉得麻烦的事——润色、搜索、提醒、代发。这是基础工具属性。
   - **趣味阶段**（近期）：管家人格切换（毒舌闺蜜/霸道总裁/二次元萌妹）、群内成语接龙、生成表情包，让社交更有趣，提升情感连接。
   - **主动关怀阶段**（远期）：从被动工具进化为主动伙伴——**主动理解情绪**（检测到消极消息→主动私聊安慰）、**主动维护关系**（好友生日→主动提醒祝福）、**主动生成群聊洞察**（分析群聊话题趋势→生成群聊月报）。这才是题目要求的"从被动响应到主动关怀"的范式转变。

## 模块三：AI 原生能力说明

### 3.1 AI 核心能力

AI 管家的设计哲学是：**"所有你觉得麻烦的事，交给管家；你只管享受纯粹的社交。"** 基于此，QQ管家的 AI 管家基于 **LLM + Tool Calling（ReAct 架构）** 构建，具备以下 5 大 AI 核心能力：

| 能力 | 技术实现 | 应用场景 |
|------|---------|---------|
| **大模型对话** | OpenAI 兼容 API（gpt-4o-mini 或同级），支持流式响应 | 自然语言交互、意图理解、情感化回复 |
| **工具调用（Tool Calling）** | ReAct 循环：理解 → 决策 → 执行 → 观察 | 19 项工具自动触发，覆盖搜索/润色/代发/生图/任务 |
| **向量语义检索** | Embedding API 生成向量 + 余弦相似度计算 | 聊天记录语义搜索、记忆检索 |
| **AI 图像生成** | DashScope 通义万相 API | 用户描述画面，管家生成图片 |
| **记忆系统** | 结构化 JSON + 向量 Embedding 双轨存储 | 长期记住用户偏好、事实、关系 |

### 3.2 AI 如何解决痛点

**去掉 AI，这个产品还能成立吗？**  
**不能。** 即时通讯的基础功能（聊天、好友、空间）可以独立运行，但产品的核心价值——降低表达焦虑、解决信息过载、实现智能提醒——完全依赖 AI 能力。具体绑定关系如下：

| 用户痛点 | AI 能力 | 绑定关系 |
|---------|--------|---------|
| 社交表达焦虑 | `polish_text` + `send_message` 口头确认 | **强绑定**：无 AI 润色，用户仍需反复编辑；无口头确认，代发风险不可控 |
| 群聊信息黑洞 | `search_messages` + Embedding 语义检索 | **强绑定**：传统关键词搜索无法理解"老师说的重点"这类语义查询 |
| 时间管理碎片化 | `create_task` + 自然语言解析 | **强绑定**：无 AI 解析，用户需手动学习 Cron 语法，门槛极高 |
| 内容创作门槛 | `suggest_moment` + `generate_image` | **中绑定**：无 AI 辅助，用户仍可手动发布，但体验大幅下降 |
| 个性化体验 | `read_memory` / `write_memory` + 向量检索 | **强绑定**：无记忆系统，管家每次对话从零开始，无法体现"懂我" |

### 3.3 AI 技术方案

#### 架构模式：双层 Agent 编排（ReAct + Plan-Execute-Observe）

QQ管家的 AI 管家采用**双层 Agent 架构**，根据请求复杂度自动路由到不同执行模式：

```
用户消息
    │
    ├── 简单请求（< 50字，无多步骤连接词）
    │   └─→ ReAct Agent（快速响应）
    │        ├─ 构建 System Prompt（SOUL人格 + 身份 + 记忆 + 工具定义）
    │        ├─ 调用 LLM → 解析 [TOOL_CALL] 标记
    │        ├─ 执行工具 → 反馈结果 → 二次调用 LLM
    │        └─ 返回最终回复
    │
    └── 复杂请求（> 50字 或 含"然后"/"先...再"等多步骤连接词）
        └─→ Plan-Execute-Observe Agent（精准编排）
             ├─ Planner：LLM 拆解为执行计划（JSON 步骤列表）
             ├─ Executor：顺序执行步骤，支持模板变量引用（{{step2.text}}）
             └─ Observer：LLM 基于执行结果生成最终回复
```

**创新点**：区别于单一 ReAct 模式，双层架构兼顾"简单问答的即时性"和"复杂任务的可控性"。例如"先帮我在群里搜索上周的作业要求，然后润色成正式语气发给班长"会被识别为复杂请求，自动拆解为：搜索 → 润色 → 代发三个步骤。

#### 技术栈详情

| 组件 | 选型 | 配置 / 说明 |
|------|------|------------|
| **LLM 服务** | OpenAI 兼容 API | `OPENAI_BASE_URL` + `OPENAI_API_KEY`，默认模型 `gpt-4o-mini`，支持一键切换至 DeepSeek / 通义千问 / 本地 vLLM |
| **Embedding** | DashScope `text-embedding-v3` | `/v1/embeddings` 接口，1536 维向量，用于记忆语义检索 |
| **图像生成** | DashScope 通义万相 | 模型 `wanx2.1-t2i-turbo`，异步任务提交 + 轮询状态（最长 60s），支持 realistic/anime/cartoon/art 四种风格 |
| **记忆存储** | PostgreSQL JSONB + 独立向量表 | 结构化记忆（`user_settings.bot_memory_facts`）+ 向量记忆（`memory_embeddings` 表）双轨并行 |
| **流式输出** | SSE (Server-Sent Events) | `POST /api/bot/stream`，逐字符打字机效果，长文本（>500字）自动加速至 5ms/字符 |
| **并发控制** | 内存级用户锁 | `acquireUserLock()` 单用户串行处理，120s 死锁检测 + 强制释放 |

#### 结构化记忆系统（5 层架构）

```
用户对话文本
    ↓ LLM 自动提取（temperature=0.3）
结构化事实（bot_memory_facts JSON）
    ├── preference（偏好）—— "我喜欢喝奶茶"
    ├── fact（事实）—— "我的学号是 20241001"
    ├── event（事件）—— "上周六参加了 hackathon"
    ├── relationship（关系）—— "小张是我室友"
    └── goal（目标）—— "这学期 GPA 要 3.8"
    ↓ Embedding API 向量化
向量记忆表（memory_embeddings）
    → 语义检索：余弦相似度 > 0.7 的 Top-5 结果
    → 可信度管理：confidence < 0.3 自动删除
    → 自动总结：超过 4000 字触发 LLM 压缩
```

**记忆管理特性**：
- **自动提取**：无需用户显式说"记住"，LLM 自动从对话中提取关键事实
- **去重合并**：相同 key 自动合并，取最高 confidence
- **语义检索**：用户问"我上次参加的比赛什么时候"，即使没提到"hackathon"关键词，也能通过向量相似度召回

#### SSE 流式对话实现

```
用户发送消息
    │
    ▼
前端设置 isTyping = true（显示三球弹跳动画）
    │
    ▼
建立 SSE 连接：fetch('/api/bot/stream', { body: JSON.stringify({ content }) })
    │
    ▼
后端调用 Agent 引擎生成完整回复
    │
    ▼
将完整回复拆分为逐字符 delta，通过 ReadableStream 推送
    │
    ▼
前端收到首个 delta → 创建 Bot 消息气泡
    │
    ▼
持续收到 delta → 实时更新消息 content（打字机效果）
    │
    ▼
收到 done 标记 → isTyping = false → 最终渲染 Markdown
    │
    ▼
如包含高危操作计划 → 管家在回复末尾口头询问"确认执行吗？"
```

**技术亮点**：流式和非流式共用同一 Agent 引擎，通过统一接口 `botPost()` 实现，无需维护两套逻辑。

#### AI 工作流程示例（代发消息）

```
用户："给小张发消息说我晚点来"
    │
    ▼
ReAct Agent 解析 → 意图：send_message，目标：小张，内容：我晚点来
    │
    ▼
调用 polish_text(content="我晚点来", style="casual")
    │
    ▼
润色结果："不好意思，我今天会晚点到～"
    │
    ▼
高危操作检测 → 命中 send_message → System Prompt 要求口头询问确认
    │
    ▼
管家回复："我准备给小张发消息：'不好意思，我今天会晚点到～'，确认发送吗？"
    │
    ▼
用户回复："确认"
    │
    ▼
ReAct Agent 再次解析 → 识别到肯定词 → 调用 send_message 工具

    ▼
后端执行 INSERT INTO messages → Socket.IO 推送 → 完成
```

#### 未来演进：从工具到伙伴——主动感知与主动关怀

AI 管家的演进严格遵循题目要求，从"被动响应"到"主动关怀"，最终成为真正理解用户的智能伙伴。

| 阶段 | 主题 | 新增能力 | 核心价值 |
|------|------|---------|---------|
| **第一阶段**<br>（当前） | **被动响应** | 润色代发、历史搜索、定时提醒、AI生图 | 基础工具属性，处理用户明确提出的需求 |
| **第二阶段**<br>（近期） | **趣味互动** | 人格切换(`role_play_mode`)、群内游戏(`word_game`)、表情包生成(`meme_generator`)、群聊日报(`summarize_chat`) | 让社交更有趣，建立情感连接，提升使用黏性 |
| **第三阶段**<br>（远期） | **主动关怀** | **主动感知场景**(`detect_intent`)、**情绪关怀**(`emotion_check`)、**关系维护**(`relationship_remind`)、**群聊洞察**(`group_insights`)、**主动帮助**(`proactive_help`)、**智能整理好友**(`organize_friends`)、**社交推荐**(`recommend_connections`) | **从被动到主动的范式转变**，实现题目要求的"主动感知场景、理解用户意图、深化情感连接" |

**为什么主动关怀是核心竞争力？**

题目要求的关键是**"从被动响应到主动关怀的范式转变"**。传统 AI 只能"你问了才答"，而主动关怀阶段的管家能"你不说，它也懂"。

**主动感知场景**（贯穿核心流程）：
- 好友连续发了多条消极消息→ 管家**主动**私聊："最近是不是有点累？需要陪你聊聊吗？"→**深化情感连接**
- 今天是室友生日→ 管家**主动**提醒："今天是小张生日，要发送祝福吗？已为你生成专属文案"→**维护社交关系**
- 空间动态有人发了求助帖→ 管家**主动**推送给可能帮助的人→"小王发了求助帖，你之前帮过类似的问题，要去看看吗？"→**贯穿动态核心流程**

**更深层的未来——跨管家社交推荐**：

当管家拥有用户的完整数据（聊天记录、兴趣标签、互动频率、群聊归属），它不仅能管理现有关系，更能主动帮用户拓展社交圈：
- **智能整理好友列表**：按亲密度自动分组（"最常联系"、"偶尔互动"、"久未联系"），并主动提醒："你和老李已经3个月没聊天了，要打个招呼吗？"
- **跨管家数据交流，个性化推荐好友**：不同用户的管家在隐私保护前提下交流数据画像，发现潜在共同兴趣——"你的管家发现你和隔壁班的小王都喜欢摄影，要不要认识一下？"
- **个性化推荐群聊**：基于用户兴趣和行为，主动推荐可能感兴趣的群聊——"检测到你对摄影很感兴趣，摄影社团正在招新，要加入吗？"

这实现了从"管理现有社交"到"拓展社交边界"的跨越，让管家成为真正的社交智能中枢。

**这就是智能伙伴的定义**：不只是等用户开口的工具，而是能读懂场景、理解情绪、主动伸出援手的伙伴。当管家能在你还没说出口时就递上你需要的东西，用户感受到的不是"AI 很智能"，而是"有人在乎我"——这才是题目要求的情感连接与使用黏性。

#### 安全与可控设计

| 机制 | 实现 | 目的 |
|------|------|------|
| **口头确认** | 8 类写操作（send_message / publish_moment / generate_image / generate_video / delete_friend / leave_group / edit_moment / delete_moment）管家先口头告知用户准备执行的操作，询问"确认执行吗？"，等待用户肯定回复后才调用工具 | 防止 AI 误操作，给用户最终决策权，交互更自然 |
| **高危意图检测** | `detectHighRiskIntent()` 正则匹配模糊请求模式（如"删掉所有人"），拦截后询问用户明确意图 | 防止恶意或误触指令 |
| **并发控制** | `userRequestLocks` Map，同一用户串行处理，120s 死锁检测 + 强制释放 | 防止并发冲突和死锁 |
| **审计日志** | `bot_audit_logs` 表异步记录：request / response / tool_calls / latency_ms / tokens_used / model / status | 全链路可追溯，支持调用链路分析 |
| **限流保护** | Bot 普通请求 30次/分钟/用户，SSE 流式 20次/分钟/用户 | 防止 API 滥用，保障服务稳定性 |
| **超时处理** | LLM 调用 90s 超时返回友好提示，用户锁 120s 强制释放 | 保障系统可用性 |
| **余额检测** | 识别 `ErrBalanceOverdue` 错误，提示用户联系管理员 | 防止服务中断 |

## 模块四：加分项

### 4.2 产品定位与竞争壁垒

#### 定位：AI 时代的智能伙伴，而非工具

QQ管家的本质不是"一个带 AI 的聊天工具"，而是**嵌入 QQ 社交生态的智能伙伴**。

题目要求的核心转变是**"从被动响应到主动关怀"**。传统 AI 产品（如通义千问、豆包）只能"你问了才答"，用完即走；而 QQ管家的管家能"你不说，它也懂"——主动感知场景、主动理解情绪、主动维护关系。这是题目要求的范式转变。

**演进路径：从工具到伙伴**

| 阶段 | 定位 | 交互模式 | 用户感受 |
|------|------|---------|---------|
| **现在** | 社交减负助手 | "帮我给小张发消息"→管家执行 | "真方便"（效率） |
| **近期** | 趣味社交伙伴 | "帮我怼回去"→毒舌回复 | "真好玩"（趣味） |
| **未来** | 主动关怀伙伴 | 群聊讨论聚餐→主动发起投票；好友生日→主动提醒祝福 | "有人懂我"（情感） |

#### 与传统 AI 助手的本质差异

| 对比维度 | 通义千问 / 豆包 / ChatGPT | QQ管家 |
|---------|--------------------------|--------|
| **响应模式** | 被动：用户提问→AI回答 | **主动**：AI感知场景→主动关怀 |
| **使用场景** | 独立 App，用户主动打开 | 嵌入 IM 核心流程（聊天/群聊/动态），自然触达 |
| **核心价值** | 效率（问答更快） | **情感**（被理解、被陪伴） |
| **社交链** | 无社交关系，孤立使用 | 嵌入好友/群聊关系链，AI 能力共享 |
| **记忆连续性** | 单会话记忆，跨会话清零 | 结构化长期记忆 + 向量语义检索，持续理解用户 |
| **用户粘性** | 低（用完即走） | **极高**（情感依赖 + 社交关系锁定） |

**核心洞察**：传统 AI 助手卖的是"智能"，QQ管家卖的是"陪伴"。当管家能在你还没说出口时就递上你需要的东西，用户感受到的不是"AI 很牛"，而是"有人在乎我"——这才是题目要求的情感连接与使用黏性。

#### 竞争壁垒

1. **情感连接护城河**：用户的聊天记录、情绪状态、社交关系都在平台上沉淀。管家越了解用户，用户越离不开——这不是换一个 AI 模型就能替代的情感依赖。

2. **主动感知技术壁垒**：从"被动响应"到"主动关怀"需要场景感知引擎（从聊天内容提取意图）、情绪识别模型、关系图谱分析——这套能力不是简单的 LLM 调用，而是深度的场景理解系统。

3. **社交关系链锁定**：AI 能力嵌入社交链（代发消息、群聊托管、关系维护），用户离开的替代成本极高。

4. **执行能力而非问答能力**：传统 AI 止步于"告诉你答案"，QQ管家能"帮你把事情做了"（发消息、发动态、管群聊），更能"主动替你想到并做到"——这是工具到伙伴的质变。
